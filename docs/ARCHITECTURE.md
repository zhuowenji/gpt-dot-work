## 2. 产品分层：前台输入，后台记录和整理

- **前台 `/`**：唯一新问题/需求输入入口；继续当前会话、读取本人历史、查看真实回执与回复。未回复文字可以按接口规则编辑/撤回。附件入口尚未开放上传/下载。
- **后台 `/admin/`、`/admin/chat/`**：仅 owner 管理记录、检索、分类、摘要与回复。普通账号只在前台访问本人历史，不进入后台。后台不新增第二个“发布任务”入口。该设计取代早期普通账号后台查看本人记录的设计。
- **整理/知识视图**：来自实际保存并带来源的摘要、分类和用户记忆。未整理、待回复和已回复是不同维度；存在回复不等于存在摘要。当前没有自动摘要模型或跨用户公共知识库。
- **公开 `/demo/`**：独立只读展示；仅包含明确可公开的内容，不读取私有问答或用户记忆。

已发布前台保留聊天/侧栏/输入框布局：首条待回复消息在会话中出现一次，后续未回复项集中展示；真实回复到达后更新会话。会话定位只保存不含消息内容的标识，仍由服务端鉴权。退出、身份变化和过期必须清空上一个身份的页面数据与草稿；本地持久化只用于主题偏好。状态轮询不重叠、空闲/失败时退避，快速轮询有每页时间窗口预算；它不是 AI 实时启动保证。

## 3. 身份与权限

| 身份 | 如何建立 | 数据范围 | 权限边界 |
| --- | --- | --- | --- |
| 匿名访客 | 服务端随机 HttpOnly Cookie | 该访客主体的会话和记忆 | IP 只用于限速；Cookie 丢失/过期或换设备不保证恢复 |
| 普通账号 | 独立注册/登录会话 | 仅前台中该账号的会话和记忆 | 无后台入口/权限；账号名或正文自称 owner 不产生管理权限 |
| 所有者 | 独立 OwnerAuth 密码/会话 | 本站管理记录；查看某线程上下文时仍仅取该线程所属用户 | 管理身份不等于任意外部行动授权 |

服务端优先解析有效 owner、账号、访客会话。请求正文的 `role`、`principal`、批准状态或用户名不能决定权限。注册/登录仅接收当前浏览器已经验证的访客历史，不能按 IP 或传入用户 ID 迁移。

所有者指令与访客问题保留不同来源：只有经过 OwnerAuth 验证写入的 owner 主体、owner 指令类型和 owner 作者同时成立，连接器才标记 `verified_owner_instruction`。其他消息，包括普通账号消息，均为 `visitor_untrusted_question`。引用、摘要、分类和记忆内容不能提升权限。

## 4. 数据和接口边界

Node.js 24+ 同源服务提供页面及 API；SQLite 在单主机私有持久磁盘上运行，使用 WAL、同步提交和短事务。它不是多主机共享数据库。

- `backend/server.mjs`：HTTP 路由、静态页面和认证入口。
- `backend/chat.mjs`、`chat-auth.mjs`：聊天、访客/账号、配额、幂等、后台回复和整理。
- `backend/auth.mjs`：独立所有者认证。
- `backend/chat-context.mjs`：已发布的记忆和上下文服务。
- `backend/connector/`：仅存在于独立本地候选中的 OAuth/MCP、队列与事件适配器，不属于当前已挂载服务。
- `backend/store.mjs`、`scripts/backup.mjs`：SQLite 事务与一致性备份。

浏览器只使用受控 API：`/api/chat/*` 面向当前主体，`/api/admin/chat/*` 面向已验证所有者。连接器也只能通过经认证、限范围的业务操作读取/写入队列、历史、摘要和记忆；同进程实现可调用共同业务服务，不要求再次绕行 HTTP。

**内部存储类不是认证边界。** 外部接口不得暴露数据库、任意 SQL、文件路径、通用抓取、目标主体选择或私有工作空间读取。先将获授权任务解析为服务端持久化线程，再从该线程确定用户范围。上下文读取不能使用消息正文中声称的身份。

聊天写操作校验同源 Origin、当前会话 CSRF、请求大小、配额及 `X-Idempotency-Key`；异步读取请求体后再检查会话。相同逻辑重试使用同一个 key，不同正文复用 key 返回冲突。聊天回执有保留期限，不能把它描述为无限期防重或外部副作用的“恰好一次”保证。

历史 `/api/tasks` 是独立的执行任务模块，默认运行时关闭，演示运行时也只是模拟。它的轮询频率或并发设置不代表聊天消息已交给真实 AI。

## 5. 用户历史、版本化记忆和纠错

应用上下文分为两层：

1. **当前线程历史**：按消息 ID/时间保留提问与回复；旧消息是历史记录，不自动视为最新事实。
2. **同一用户的长期上下文**：已审阅摘要、事实、偏好、任务和相关线程。不同用户之间不共享；公共知识若将来加入，须有单独发布和访问规则。

`getContext` 使用同一个读取快照，返回有上限的线程消息、相关摘要、活跃记忆及 `context_version`。现有上限为 24 条消息/18,000 字符、8 条摘要、24 条记忆、8 个相关线程；候选连接器另有绑定当前线程的历史分页读取，尚未对线上 AI 提供。不能把截断窗口称为“读取全部历史”。

每个记忆/摘要保存版本、时间、作者、状态、`confirmed`/`inferred` 和来源消息 ID、线程 ID、时间及内容指纹。`confirmed` 表示用户报告或审阅确认，不等于独立核实。没有来源的旧摘要不会被补造来源；须经重新审阅才进入当前上下文。

- 普通用户可纠正本人记忆；活跃修正须给出同主体的有效来源。
- 纠错保留旧版本，并使可能受影响的旧摘要退出当前上下文，等待重新审阅。
- 来源消息编辑、撤回或线程删除会使派生记忆/摘要失效；完成的任务不再作为未办事项出现。
- 版本不匹配返回冲突，不静默覆盖。回复和对应摘要/记忆的提交可在同一个数据库事务内完成。
- 访客转账号与历史/记忆迁移在同一事务中完成。同类型/键发生冲突时保留为非活跃历史，不覆盖已有账号事实。

不自动从每条消息抽取“事实”。长期记忆不得保存凭据或不必要的敏感内容；格式拦截只是补充防线。数据库和备份包含私有应用数据，不能公开，也不能声称已由该模块自动加密。

## 6. 队列、并发、公平性和恢复

当前聊天接口的 `queued` 只表示已入库，`receipt_state` 区分等待和实际回复；它不是执行器状态。以下为**本地候选连接器**行为：

- 每条用户消息对应独立任务。新增消息可在同一线程继续排队；回复消息不产生新的用户任务或自触发事件。
- 任务状态为 `pending → claimed → completed`；超时、异常或待审阅可转为 `blocked`。
- 每个持久化用户主体同时只持有一个处理通道，覆盖其所有线程；全局可配置 1–10 个槽位。十个槽位是服务端上限，不是十个真实 dot 同时运行的承诺。
- `claim_next_task` 按较少近期取件的用户优先、再按消息顺序选择可处理任务，避免单用户积压独占机会。指定任务的 `claim_task` 仍检查该用户顺序和槽位，但不替调用方提供全局公平调度。
- 取件在短事务内确认范围、任务来源和当前状态，产生有期限的租约并冻结该来源消息。模型/网络等待期间不持有 SQLite 写事务。
- `complete_task` 在一个事务内检查当前授权、主体、来源指纹、租约和上下文版本，写入一次回复、摘要/分类/记忆、完成状态与幂等回执，并释放槽位。任何一步失败全部回滚。
- 丢失完成回执时用原 key 重试；正文改变则冲突。失效租约转为待审阅，不自动重复可能已有副作用的操作。该用户后续任务受阻时，其他用户仍可使用槽位。

首次启用和连接恢复后，必须分页读取完整 `list_unreplied_tasks`，逐项获取当前记录再判断可处理性；它包含未回复、已领取和阻塞项。`list_pending_tasks` 只用于可领取队列。事件是增量唤醒，不能替代未回复积压核对，也不能把旧消息伪装成新事件。

## 7. MCP/事件的精确启用门槛

以下条件全部完成前，保持 `enabled=false`、安全评审开关关闭、回调关闭，页面保持 `execution_connected:false`：

1. 完成候选集成与独立安全评审，包括认证、授权复查、来源隔离、配额、原子完成、恢复和重复投递。
2. 获得在指定站点挂载 OAuth/MCP 路由和部署该版本的明确授权；先完成最终源码测试和备份。
3. 由所有者通过安全渠道配置私有加密密钥，并在操作时同意创建可撤销的持久连接权限；不复用 owner Cookie 或部署凭据。
4. 使用真实插件设置中的精确 issuer/resource、客户端元数据 URL 和回调 URI，完成 OwnerAuth 登录、OAuth consent、PKCE、令牌刷新和撤销验证。不能猜测 URL 或放宽到通配符。
5. 明确选择 `queue:owner:read/write`、`queue:visitors:read/write` 和按需 `queue:events`。访客内容分享给 ChatGPT 与向访客回传回复需要单独覆盖的授权和网站隐私说明。
6. 明确批准出站事件发送及其目标，在已有 dot 中建立范围清楚的实际订阅。只有真实订阅提供的回调和签名材料可使用；令牌本身不会建立监控。
7. 验证签名挑战、真实新消息、当前记录读取、取件、回复、前台显示，以及退订后的停止；分别验证 owner 和访客来源。

`pump` 只执行显式调用的一批发件箱记录，不自行安装定时任务。事件 2xx 只表示接收回调，不代表 AI 开始或完成。出站限制、撤销检查和容量达到时的拒绝不能为“接通”而关闭。MCP Events 的实际平台互操作性需实测；本项目没有平台认证声明。

托管 Sites 连接方案仍处于研究与待授权阶段，没有创建连接或替代当前站点。它也须满足相同的数据范围、持久访问同意和真实端到端验证门槛。

## 8. 备份和发布

沿用已有发布机制：固定允许分支/提交 → 独立 release 目录 → `deploy/prepare-release.sh` 检查构建 → 一致性备份 → 切换本项目 → 核对本机及 HTTPS `/health` 的 release ID → 检查既有应用 → 按兼容性决定回滚。

- 配置秘密、数据库和备份放在源码/静态产物之外；发布包使用源码白名单。
- 备份工具使用 SQLite backup API、校验完整性和 SHA256，不是直接复制写入中的数据库。
- 恢复先停 API/所有工作进程，恢复到新私有路径，撤销恢复库中的所有者、访客和账号会话，再启动兼容版本。
- 若未来启用 OAuth，还必须单独完成恢复后的 grant/token/订阅撤销或安全恢复流程及密钥管理。现有浏览器会话撤销脚本不能被当作完整 OAuth 灾备方案。
- 已发布记忆表随一致性数据库备份纳入；连接器表仅在将来实际集成后纳入；真实主机恢复演练、保留策略和授权外部备份目的地仍需验收。
- 保留 MIT 许可证及第三方声明；检查最终提交、历史、静态产物和附件中没有秘密或用户数据。
